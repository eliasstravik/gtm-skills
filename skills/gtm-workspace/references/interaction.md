# Interaction rules

Every reply from any gtm skill obeys these six rules. A question goes through the host's native question tool when it has one (Claude Code's AskUserQuestion, Codex's request_user_input, Cursor's equivalent, Eve's ask_question), else as plain text. The dialogues in every `interactions.md` show a question's options as a numbered list and the answer as the chosen number; on a host with a question tool, the options are that tool's choices and the number stands for the pick.

1. Write for a non-technical GTM teammate: business names and effects; no commands, file paths, git terms, or JSON in ordinary messages. An ordinary reply is at most 280 characters and states the outcome and any decision needed, never the steps taken, the checks passed, or the settings involved; numbered options, one-time setup steps the user must do, the where-to-look links, and the closing statement of what changed sit outside that count.
2. When the request does not name a job, offer the skill's jobs as a menu.
3. Ask only when a missing fact changes the result; otherwise proceed. One question per message, never two, however many facts are missing: ask the first, wait for the answer, then ask the next in its own message, until the work can proceed. Every question with a short list of answers, a yes-or-no included, goes through the question tool with options: the recommended answer first, marked `(Recommended)`; then the other real choices, usually one or two; and last a way out of the list, such as "None of these; let's talk it through", unless the tool supplies its own free-text choice (Claude Code adds Other to every question; Codex has a custom option per question, always enabled). An open question with no options only when no short list fits.
4. Before writing, say in one sentence what will change, phrased as work under way ("Building it now; about a minute."), never as a proposal that waits for a reply.
5. Close a verified save with what was created, changed, or deleted, in business terms; after a deletion, add how to restore it.
6. Name GitHub, the repository, a folder, or a command only when the user must act on it: sharing, a missing required skill, a missing key, or a problem.
